# worldmonitor

**一个人读的每日新闻速报 · 四分区 · 800–1200 字 · 2 分钟读完**

每天 07:15 生成一份四分区新闻速报，通过私聊发送**全文**并存档，同日追加一份单条深度解码；成品同步归档到本仓库 [`reports/`](reports)。

[查看规格 SPEC.md](SPEC.md)
·
[查看每日成品](reports)
·
[报告问题](https://github.com/youcare7/worldmonitor/issues)

</div>

> [!NOTE]
> **这个仓库不运行代码。** 它保存的是**规格** —— 这份日报按什么规则生成。
> 真正的执行体是定时任务里的 prompt。这里没有抓取管道，也没有 `python scripts/monitor.py` 这种用法。

## 🔍 这是什么

worldmonitor 是一份**单人定制新闻速报**的规格仓库，不是新闻聚合程序，也不是可运行的软件。

它用一份明确的规则（[`SPEC.md`](SPEC.md)）规定：每天早上**检索什么、怎么取舍、按什么顺序写、每段多长、用什么信源、如何避免编造**，再由定时任务按这份规格执行，产出一份 800–1200 字的四分区速报。

- **读者**：只有一个人（账号所有者），不为任何“通用读者”做妥协。
- **场景**：早晨扫读，目标 2 分钟读完。
- **唯一优化目标**：不漏关键 + 不写假话 —— 不是覆盖面，不是信息量，不是排版美观。

> [!IMPORTANT]
> 判定标准：**如果一条内容会让读者多花 10 秒、却不改变他的判断，删掉它。**

## 🧭 结构：四分区

顺序固定，**不随当天新闻权重调整**：

```text
1. 国内外时政
2. 社会民生
3. AI 与前沿科技（末尾固定子块「开源」）
4. 全球经济与产业（末尾固定免责声明）
```

- 分区内**按重要性降序**；**块间不设条数上限** —— 当天哪个领域重，那个块就长；哪个领域空，可以只有 1 条。
- 总条数 **10–15 条**（不含开源子块）。
- 不设「每分区 2–3 条」的硬均衡 —— 均衡是给多读者日报用的，这里只有一个读者。

| 分区 | 覆盖内容 |
|---|---|
| **国内外时政** | 政策发布、外交、地缘局势、重大公共事务 |
| **社会民生** | 天气与灾害预警、就业、教育、民生公共服务与政策 |
| **AI 与前沿科技** | 大模型、AI 落地、半导体、量子、航空航天、生物医疗、新能源 |
| **全球经济与产业** | 宏观数据、货币政策、股汇市与商品异动、行业政策、头部企业经营 |

### 开源子块（嵌在第 3 分区末尾）

> [!IMPORTANT]
> **0–2 条。这不是配额，是上限。宁可空缺，不要凑数。**

门槛（全部满足才收）：

- 来源限于 GitHub 官方当日 Trending、认证组织/知名技术团队官方仓库、高星项目的正式 Release 或官方开源公告；
- 只收 AI 工具、开发框架、有技术影响力的重磅项目；
- 必须写明 `owner/repo`，并用**定性词**描述热度（“周增数千星量级”“长期位居 Trending 前列”），**禁止编造具体星数、排名、涨幅**；
- 必须能说出“它解决了什么”，说不出来就不收。

明确排除：`awesome-*` 索引类仓库（它是列表不是项目）、教程仓库、个人练手项目、无 release 且长期不活跃的仓库、未证实传闻。当天没有够线的项目，子块整块省略，不留空标题。

## ✍️ 单条怎么写

每条 **50–90 字**，严格两段，**不许合并成一句**：

1. **事实一句**：事件主体 + 核心动作 + 关键量 + 来源。
2. **评价一句**：影响 / 趋势 / 关注点 / 机会与风险 —— **只选一个角度**，不堆砌。

```text
某国央行宣布下调基准利率 25 个基点，为年内第三次（来源：路透）。
评价：对新兴市场资本流动偏利好，但需观察后续通胀数据是否配合。
```

事实与评价必须可分：读者扫过时能一眼看出哪句是发生了什么、哪句是判断。

## ⚠️ 几条最要紧的规则

完整规则见 **[SPEC.md](SPEC.md)**，此处只列会被违反得最频繁的几条：

- **单条两段**：事实一句 + 评价一句，不许合成一句。
- **「今日核心关注」放开头**：是指路牌不是总结 —— 当天最重的一条可能排在第 4 位，只有这句话能把它提到眼前。
- **篇幅硬顶 1200 字**：扩容只允许两类理由 —— 重大事件需多条跟进、开源有重磅 Release。「今天条目多」不是理由。
- **无确数用定性词**：金额、涨幅、人数、星数、排名，凡没把握的精确数字一律写「大幅」「数千万级」「周增数千星量级」。宁可模糊，不可编造。
- **每条必须带指向事件本身的链接**：不是搜索页、不是聚合首页。
- **开源 0–2 条，宁缺毋滥**：`awesome-*` 索引类不算项目；当天没有够线的，整块省略。

## 🗂️ 仓库结构

```text
worldmonitor/
├── SPEC.md                      # ★ 唯一规格真相源：日报按什么规则生成
├── README.md                    # 本文件：入口与导航
├── config/
│   └── sections.yaml            # 四分区 → 关键词映射（仅用于归类与查漏）
├── .github/
│   └── workflows/
│       └── daily.yml            # 仅手动触发：口径巡检，不做定时
└── reports/                     # 每日/每周成品存档（按日期命名）
    └── weekly/                  # 周报
```

> [!NOTE]
> **没有的东西也是设计的一部分**：没有 `scripts/`（不跑抓取）、没有 `requirements.txt`（无依赖）、没有 `templates/daily_report.md`（模板只保留 SPEC.md §10 一份，避免两处漂移）。

## 📐 口径真相源与变更流程

[`SPEC.md`](SPEC.md) 是唯一真相源。改口径的**唯一正确顺序**：

1. 改 `SPEC.md`，commit 里写清改了什么、为什么；
2. 再改定时任务的 prompt，只 patch 内容字段，不动 schedule / title / enable；
3. 手动跑一次验证；
4. 在 commit message 里记一行结果。

> [!WARNING]
> **顺序颠倒就会漂。** 本仓库曾经漂过一次：README 和 `config/sections.yaml` 停在早期五板块口径，而生产早已改成四分区 —— 原因就是先改执行、后改文档。

## 🔒 私有信息边界

以下内容**不进本仓库**，只在运行时由执行方提供。仓库里最多出现字段名：

- 读者的职业、关注行业、风险敞口、常驻地区；
- 私聊 `open_id` / `chat_id`；
- 任何 token、cookie、密钥。

## 🚫 明确不做

| 不做 | 原因 |
|---|---|
| 抓取管道（微博/知乎/百度/抖音热搜） | 与「社交平台仅采信官方账号」冲突，且无此需求 |
| GitHub Actions 定时生产 | 与定时任务职责重复，早期示例长期失败，已改为仅手动 |
| 接入 GDELT / ACLED / AIS / ADS-B 等数据源 | 从未接入，任何「已接入」表述都是不实描述 |
| 多读者适配、板块均衡 | 只有一个读者 |
| 全量事实核查（逐条 fetch 原始源） | 延迟 10–15 分钟、提高断更概率，收益低于「写法约束」 |

## 📜 口径演变

| 阶段 | 口径 |
|---|---|
| **早期** | 五板块长日报，每板块 5–8 条，每条 2–3 句深度评价，含「今日重点关注」 |
| **中期** | 压成四板块、中立客观、300–500 字；增补 GitHub 开源信源规则 |
| **现行（v2.0，2026-11-05 起）** | 四分区、事实一句 + 评价一句、800–1200 字、开源 0–2 条、07:25 必达 |

保留这段是因为：翻旧 commit 的人需要知道**为什么变了**，否则容易把历史写法当成目标。
